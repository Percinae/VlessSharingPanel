# Выпуск по тегу на VPS РФ

Workflow [release.yml](../.github/workflows/release.yml) запускается при публикации тега `vMAJOR.MINOR.PATCH`, совпадающего с `Cargo.toml`. Он принимает только коммит из `main`, запускает форматирование, Clippy, тесты приложения и отката, собирает статический `x86_64-unknown-linux-musl` бинарник, проверяет SHA-256, копирует его по SSH и атомарно переключает `/opt/vless-panel/current`. Если сервис не отвечает на локальный `/healthz`, предыдущая версия восстанавливается автоматически. Данные в `/var/lib/vless-panel` при обновлении не трогаются.

Панель запускается отдельным пользователем только на `127.0.0.1:3000`. У деплой-пользователя есть право перезапустить **только** `vless-panel.service`; ему не нужен root, доступ к Xray, WireGuard или секретам базы. Порт `443`, занятый VLESS/REALITY, workflow не меняет.

## Однократная подготовка VPS

1. Убедитесь, что VPS имеет архитектуру `x86_64`, Ubuntu с `systemd`, команды `curl`, `sudo`, `visudo`, `sha256sum`, `ss`, `ssh-keygen` и свободный локальный порт `3000`. Нужен рабочий SSH-доступ с GitHub-hosted runner. Текущая Cloud-среда получает `Connection refused` на `201.34.141.166:22`; до исправления сетевого доступа workflow также может не подключиться.
2. Создайте **отдельную** пару Ed25519 для деплоя. Скопируйте только публичную часть на VPS через свой обычный SSH-доступ. Приватный ключ сохраните для GitHub Secret; не добавляйте его в репозиторий.
3. На VPS из проверенного checkout этого репозитория выполните:

   ```sh
   sudo bash deploy/bootstrap.sh 'https://ВАШ_АДРЕС:8444' /path/to/vless-deploy.pub
   ```

   Скрипт создаёт пользователей `vless-panel` и `vless-deploy`, каталоги, `systemd` unit, ограниченное правило `sudoers` и файл `/etc/vless-panel/panel.env`. Адрес должен быть будущим доверенным HTTPS origin без пути. Если надёжного HTTPS-адреса пока нет, не публикуйте ссылку получателям.

4. Сверьте fingerprint SSH host key VPS по доверенному каналу (например, через консоль провайдера и `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`). Строку `known_hosts` для адреса/порта получайте только после сверки; workflow использует `StrictHostKeyChecking=yes` и не принимает неизвестный ключ автоматически.
5. В GitHub `Settings → Environments → production` создайте:

   | Тип | Имя | Значение |
   | --- | --- | --- |
   | Variable | `VPS_HOST` | SSH-адрес VPS РФ |
   | Variable | `VPS_USER` | `vless-deploy` |
   | Variable | `VPS_PORT` | SSH-порт, обычно `22` |
   | Secret | `VPS_DEPLOY_KEY` | приватный ключ отдельной пары Ed25519 |
   | Secret | `VPS_KNOWN_HOSTS` | проверенная строка `known_hosts` для этого адреса и порта |

   Ограничьте environment и теги `v*` правилами репозитория, разрешив выпуск доверенным участникам. Если нужен полностью автоматический деплой, в `production` не должно быть обязательного ручного reviewer approval. Не создавайте тег до установки и проверки workflow из `main`.

6. Один раз инициализируйте базу, ключ шифрования и пароль с TOTP на VPS. Бинарник появится в `/opt/vless-panel/incoming/<тег>/vless-sharing-panel` после первой попытки workflow; до инициализации деплой корректно остановится. Тогда из своего SSH-сеанса выполните:

   ```sh
   sudo -u vless-panel /opt/vless-panel/incoming/v0.1.0/vless-sharing-panel --data-dir /var/lib/vless-panel init
   ```

   Замените `v0.1.0` на фактически выпущенный тег. Введите длинный пароль **в своём терминале**, сохраните TOTP-секрет в приложении-аутентификаторе и сделайте защищённую резервную копию каталога данных. Затем повторите упавший deploy job в GitHub Actions. Дальнейшие теги обновляются без этого шага.

## Выпуск и проверка

Обновите `version` в `Cargo.toml`, проверьте и объедините изменения в `main`, затем создайте тег на коммите из `main`:

```sh
git tag -a v0.1.0 -m 'Release v0.1.0'
git push origin v0.1.0
```

Для следующего выпуска используйте новый номер версии и тег. Повторно использовать старый тег с другим бинарником скрипт не позволит. На VPS проверьте `systemctl status vless-panel.service` и `curl -f http://127.0.0.1:3000/healthz`.

Workflow проверяет **локальную работоспособность панели**. Публичный HTTPS reverse proxy и сертификат для IP/домена настраиваются отдельно, не занимая действующий `443` Xray. Перед раздачей ссылок проверьте внешний HTTPS-адрес из сети получателя. Не включайте HTTP в `PANEL_PUBLIC_URL` для VPS.
